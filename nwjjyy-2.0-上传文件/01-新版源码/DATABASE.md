# 数据、权限与恢复

数据库结构按 [迁移文件](supabase/migrations) 的文件名顺序更新。第二位成员由管理员授权。成员标识来自 Supabase Auth 用户的 UUID，故事中的显示名来自成员表。

| 表 | 内容和关系 |
| --- | --- |
| members | Auth 账号、显示名、角色和启用状态，每种角色最多一位 |
| categories | 可改名和归档的分类，已有故事继续保留原分类 |
| stories | 日期、标题、正文、摘要、作者、分类、精选状态、封面和修订号 |
| perspectives | 故事与补写者组成唯一键，各人独立编辑自己的视角 |
| diaries | 日期、作者、心情、草稿与首页展示开关 |
| media | 附属故事、日记或独立相册记录，包含说明、顺序、类型和大小 |
| promises | 创建者、愿望、期待日期、完成日期和完成后关联的故事 |
| anniversaries | 自定义日期、首页显示和周年倒计时开关 |
| storybook_settings | 私人首页介绍、独立相册封面和纪念日时区 |
| chapters、chapter_entries | 章节、故事归类、封面和排序 |
| footprints、trip_entries | 城市、相见日期和关联故事 |
| photo_notes、photo_collections、photo_collection_items | 照片背面、主题合集与顺序 |
| story_relations、story_revisions、annual_books | 故事关联、文字修订历史与年鉴编辑 |
| private.letter_envelopes、letter_bodies、letter_assets | 信封、正文与私人附件，由信箱函数按参与者及解锁时间读取 |

主要记录使用 UUID。发生日期为 PostgreSQL date，创建、发布和修改记录使用带时区的时间戳。纪念日按配置时区求当地日期后做日历日差，2 月 29 日在非闰年以 2 月 28 日计算。

## 权限如何生效

- 浏览器只携带公开客户端密钥和当前成员的会话令牌。各业务表启用 RLS，并显式约束匿名和已登录用户所获的表权限。Auth 用户需要有启用的成员记录才能读取私人数据。
- 成员只能以自己为作者写入。共同记录者可写自己的故事、日记、约定和视角，读取两位发布的内容。作者与管理员可读取草稿。管理员管理精选、分类、纪念日、首页和共同记录者的授权。
- 原图和预览图在私有存储桶中。路径由上传者 UUID、媒体 UUID 和固定文件段组成。数据库按所属记录的发布、移除状态校验读权限。网页使用经身份验证的下载和临时 Blob URL。RLS 同时约束上传、覆盖和删除。
- 新附件先写暂存元数据，再写原图和预览。保存故事或日记时，数据库在一个事务里检查文件存在、保存顺序和封面，并提交正文。修订号阻止旧编辑覆盖新修改。软删除后已保存的文件继续保留，作者或管理员可以恢复记录。
- 保存一条约定可以关联已发布的故事。时间轴按发生日期分页，相册用数据库函数按照片或父记录日期筛选。未完成的附件可在管理中心清理。已保存内容需要永久清理时，由项目管理员先备份，再通过管理工具逐项处理。 [Supabase RLS 与授权](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 信件附件用独立的 storybook-letters 私有存储桶。寄出前只有作者可读。收信人收到并打开信封后才能读正文与附件，时间胶囊的解锁由数据库时钟判定。
- 隐藏故事保留给有访问权限的成员，在日常时间轴、章节、搜索、相册、随机回忆和年鉴中隐藏。已登录成员可以通过专属链接阅读。
- 生产构建的离线缓存只收录公开网页外壳和打包后的资源。登录请求和私人故事、照片、信件通过实时请求读取。

## 导出和恢复

迁移共享故事书时，用管理员账号打开 **更多 → 备份与导出**。两位暂停编辑时准备备份，把同一次下载的 JSON 和全部媒体 ZIP 放在同一目录，保持 ZIP 文件名原样。每批媒体约不超过 40 MB，JSON 记录了每批文件和关联关系。管理员导出包含草稿、回收站、已保存的媒体及新版章节、相见、年鉴、照片和历史记录。Auth 账号须在新项目重新建立。信箱的个人 JSON 供参与者留存，无自动导入功能，附件文件需另行保存。

从零恢复：

1. 新建一个专用 Supabase 项目，按顺序执行全部迁移，确认两个存储桶都是私有的。按 [接入步骤](SETUP.md) 设置邮箱密码登录，先创建两位新 Auth 用户。此时业务成员表应为空。恢复会把成员授权一并写入。
2. 在私人备份目录写一个 UID 映射 JSON。每个键是管理员导出中 members 里的旧 id，每个值是同一个人在新项目里的 User UID。两个人各有一条，只有管理员时填一条。
3. 在开发机通过临时环境变量准备下列信息，再运行恢复工具。Vite 只读取 VITE_ 前缀，表中的变量由 Node 恢复工具使用。终端里的敏感值由你自己输入。恢复工具只接受同一个项目的 Supabase 标准 HTTPS 地址与其 **Direct connection**。如果本机无法直连该项目的 PostgreSQL，需要在能连接直接数据库地址的机器上运行。

| 变量 | 含义 |
| --- | --- |
| STORY_RESTORE_URL | 新项目的标准 HTTPS URL |
| STORY_RESTORE_SECRET | 新项目用于可信管理端的 sb_secret_ 密钥 |
| STORY_RESTORE_DATABASE_URL | 新项目 Connect 面板的 Direct connection 字符串 |
| STORY_RESTORE_DATABASE_CA_FILE | Supabase 数据库设置中下载的根证书文件路径，用于验证 TLS 证书 |

~~~powershell
node scripts/restore.mjs "备份目录/nwjjyy-records-时间.json" "备份目录/member-map.json" --confirm-new-project
~~~

4. 工具先检查备份完整性和目标项目，然后上传文件、恢复记录、重配作者和权限。媒体阶段失败后可以用同一份备份重试，工具会核对已存在的文件内容。数据库操作失败会回滚元数据事务，已经上传的私有文件可在下次恢复时重用。工具只接受没有成员和内容的新项目。
5. 在本地将前端指向新项目，分别登录检查故事、照片、录音、日期和成员角色。确认完毕后，再更新 GitHub Actions 的两项公开配置并重发网站。保留旧项目与离线备份直到核对完成。

恢复测试在独立的本地 PostgreSQL 实例间运行，覆盖 V1、V2 两种备份格式。测试核对了媒体字节、作者映射、照片背面、章节、年鉴、相见记录、NFC 设置和修订历史。正式 Supabase 项目的数据库和媒体传输需要接入后验收。

[Supabase 数据库连接与根证书](https://supabase.com/docs/guides/database/connecting-to-postgres#ssl)
